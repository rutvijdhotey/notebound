01The forces that shaped everything

Notebound is a trip-centric journal. You start a trip, capture notes into it — voice, text, photos — and when the trip ends, Claude writes the trip up as a blog post with an itinerary and the photos it judged strongest.

Almost every structural decision in this codebase traces back to one of four constraints. They are worth stating first, because they explain choices that would otherwise look arbitrary.

  • The capture moment is unrepeatable. A note taken on a mountain pass with no signal cannot be re-taken later. Saving must never depend on the network, and never block on it.
  • One developer, no ops. There is no team to run infrastructure. Anything requiring a server process to be babysat was rejected in favour of managed primitives — Postgres, RLS, triggers, cron, edge functions.
  • Private by default, public by exception. A travel journal contains where you were and when. The only data that ever leaves the owner's boundary is an anonymised place aggregate, and only after the trip completes.
  • Free-tier economics. Voice runs on-device (free) rather than a transcription API. Classification runs on Haiku; only the once-per-trip blog spends Opus with vision.

Read the rest of this paper with those four in mind and the architecture reads as one argument rather than a pile of libraries.

02System context

There are three planes: the device, one Supabase project, and the Anthropic API. Nothing else. There is no backend service of our own, no queue broker, no CDN we configured, no analytics pipeline.

Decision
Supabase as the entire backend, not a database with a service in front of it
Alternatives
Firebase; a hand-rolled Node/Postgres API on Fly or Railway; Expo + a serverless API layer.
Why
Auth, row-level authorization, object storage, change streaming, cron and function hosting arrive as one thing with one connection string. Authorization lives in the database, so there is no application tier that can forget to check ownership — the check runs whichever path reaches the row.
Cost
Real vendor lock-in: RLS policies, triggers, SECURITY DEFINER functions and pg_cron jobs are the application. Free-tier projects auto-pause after ~7 days idle, which required a keep-alive job (§12).

03The client shell

React Native 0.81.5 on Expo SDK 54, React 19.1, TypeScript in strict mode, New Architecture (Fabric/TurboModules) enabled, iOS deployment target 16.4, bundle com.rutvijdhotey.notebound.

The project runs the prebuild workflow rather than the managed one: ios/ and android/ are generated from app.json and are gitignored, regenerated with npx expo prebuild --clean. That keeps the native projects disposable while still allowing native modules that Expo Go cannot host — on-device speech recognition and Apple Maps in particular.

Decision
On-device iOS speech recognition instead of a transcription API
Alternatives
Whisper via an edge function; a hosted STT vendor.
Why
Free, no per-minute cost, no audio ever leaves the device, and it streams interim results so the capture sheet can show words appearing as you speak. Audio is the single largest payload the app would otherwise upload — over a hotel Wi-Fi or foreign roaming, that matters.
Cost
iOS-only quality, English-locked (lang: 'en-US'), and the module needs a real build. useVoiceRecording carries three defensive event handlers — end, nomatch, error — because iOS can end a session without ever emitting a final result, which would otherwise strand the mic button on "Listening…".

Navigation: a stack over a pager, not a tab navigator

Navigation is three nested pieces. AppNavigator switches on session presence — no session renders the auth stack, a session renders MainStack. There is no "logged out" route inside the app; signing out unmounts the entire authenticated tree, which makes stale-state leaks structurally impossible.

TabNavigator is not @react-navigation/bottom-tabs. It is a PagerView with a hand-built tab bar, so the four tabs (Home · Explore · Search · Blog) can be swiped between as well as tapped. The tab bar is a plain row of Pressables driven by pagerRef.setPage().

The capture button lives above the navigator, not inside a screen. MainStack renders a View containing the stack, then FloatingCaptureButton, then NoteCaptureSheet as siblings — so capture is reachable from every screen at every depth, and a note can be started from a blog post as easily as from Home. Tap opens the sheet; long-press opens it and starts recording immediately.

MainStack is also where three background behaviours are wired, because it is the outermost component that exists exactly once per authenticated session: queue draining on mount, on network reconnect, and on AppState returning to active; and the location sweep and place-name backfill, run once per session in that order (§08).

Theme

A single dark palette in src/theme/index.ts — warm amber #C8703A on #111111 — exported as flat token objects (Colors, CategoryColors, Typography, Spacing, Shadows, BorderRadius). No styling library. Trips with no cover photo get a deterministic gradient chosen by hashing the trip name, so the same trip is always the same colour without storing anything.

04Code layering, and where the tests live

The src/ tree follows one convention with real teeth: every service is split into a *Service.ts that does I/O and a *Helpers.ts that is pure. All the decisions live in the helpers, all the network lives in the services.

Decision
No Redux, no React Query, no state library at all
Alternatives
TanStack Query for server cache; Zustand or Redux Toolkit for app state.
Why
The server already pushes changes. Each list hook does exactly three things: fetch once, subscribe to a filtered Postgres change stream, and reduce INSERT/UPDATE/DELETE into local state. A cache library would sit between the push and the render and mostly need invalidating by hand. Only one piece of genuinely global state exists — the auth session — and that is a context.
Cost
The reducer shape is copy-pasted across useTrips, useNotes, useBlogPosts and useTripDetail. Deduplicating it into a generic hook is an obvious future refactor that has not been worth doing yet.

Two subtleties in the hooks are worth calling out because they were bugs first. Channel names carry a per-instance random suffix (trips:${userId}:${instanceId}) because two mounted copies of the same hook silently collided on a shared channel name. And useSignedPhotos joins its ref array into a single string key so the effect re-runs on content change rather than on every new array identity.

Six tables and one view, built up across 27 migrations. Migrations are the source of truth, numbered NNN_description.sql, applied through the Supabase MCP server and committed alongside the code that depends on them; src/lib/database.types.ts is regenerated after every schema change.

RLS is the authorization layer

Every table has row-level security enabled and policies scoped to auth.uid(). Two of them do more than compare a user id, and both are load-bearing:

  • notes_insert_own also asserts exists (select 1 from trips where id = trip_id and user_id = auth.uid()). Matching user_id alone would let a crafted client attach their own note to someone else's trip.
  • notes_update_own gained the same clause in migration 013, when moving notes between trips shipped. Until then, UPDATE had a weaker check than INSERT — a note could be created correctly and then moved onto a foreign trip.
Decision
Invariants belong in the database, not in the app
What that means
trips.note_count is maintained by a trigger on insert, delete and trip-changing updates. updated_at is a trigger. Categories, statuses, ratings and location sources are CHECK constraints, not TypeScript unions — the unions in *Helpers.ts narrow the generated row types to match what the constraint already enforces. Ratings carry a second constraint: a rating may only exist on a rateable category, so a category switch cannot leave an orphaned star count behind.
Why
There are three write paths into notes — the app, the offline drain, and the tagging pass — and later a fourth (edge functions with the service role). A rule enforced in one of them is not a rule.
Cost
Business logic in PL/pgSQL is harder to test and to review than TypeScript. It is covered by SQL test files under supabase/tests/ rather than by Jest.

Every trigger function is hardened the same way: set search_path pinned, and EXECUTE revoked from public, anon and authenticated. In Supabase, a SECURITY DEFINER function in the public schema is otherwise reachable as a REST endpoint — /rest/v1/rpc/handle_new_user — and CREATE OR REPLACE re-grants the default, so migrations 002a and 003a exist purely to re-revoke.

Realtime, and the replica identity trap

trips, notes and blog_posts are in the supabase_realtime publication. Migration 009 sets REPLICA IDENTITY FULL on all three: with the default identity, a DELETE event carries only the primary key, so a subscription filtered on user_id=eq.… never matches the delete and the removed row lingers in the list forever. That bug showed up twice — a deleted trip still in the capture picker, a discarded draft still in the Blog tab — before the cause was found.

06The offline-first write path

This is the heart of the app. Capture never touches the network. It writes to a durable local queue and returns; everything after that is a background drain that can fail and retry forever without losing the note.

Decision
A client-minted offline_id with a unique constraint, instead of server-assigned ids
How
expo-crypto mints a UUID before the note is queued. notes.offline_id is not null unique, and the drain writes with upsert(row, { onConflict: 'offline_id', ignoreDuplicates: true }).
Why
It makes the drain idempotent by construction. A drain that uploads a note and then dies before removing it from the queue is harmless: the next drain re-sends it and the database ignores the duplicate. No de-duplication logic, no "did it commit?" ambiguity, no tombstones.
Cost
Two identities per note. The photo queue has to key against either offline_note_id or the database id depending on which exists yet, which is the messiest part of photoUploadService.
Decision
Two separate queues, not one
Alternatives
A single queue with an item type; upload photos synchronously before saving the note (the original design).
Why
Text and photos have different failure profiles. A note is a few hundred bytes that either lands or does not; a photo is hundreds of kilobytes that may fail repeatedly on a weak connection. Coupling them meant a photo note could not be captured offline at all, and the capture sheet blocked on upload. Separating them let capture return instantly and gave photos their own retry budget (MAX_ATTEMPTS = 5) and their own UI state.
Cost
drainPhotoUploads has genuinely tricky group-resolution logic: a note's photo_urls is patched only once every photo in its group has either succeeded this run or exhausted its attempts, so a half-uploaded note never renders a partial strip.

The feed is a merge, not a query

useNotes returns FeedItem[] — a union of { kind: 'note' } from Postgres and { kind: 'pending' } from the local queue. Pending items whose offline_id already exists in the server rows are dropped, so a note visibly promotes from local to synced without flicker or duplication. The merged list sorts on occurred_at ?? captured_at, so a photo's EXIF capture time — which can be weeks before the note was typed — places the note where the experience actually happened.

07The photo pipeline

Photos are the only large binary the app handles, and their storage model was rewritten once, under pressure, after a security audit. That rewrite is the most instructive change in the codebase.

Originally the photos bucket was public: upload, call getPublicUrl, store the URL in notes.photo_urls, render it. Simple, fast, and wrong — the SELECT policy that made public URLs work also backs the storage list API. Anyone holding the anon key, which ships inside the app binary, could enumerate the bucket root to get every user's UUID folder, then every note id, then every filename.

The rewrite touched every read path, so it is centralised in two files:

  • photoRefs.ts — pure. toStoragePath() normalises anything the database might hold: a bare path, a path with the cover photo's ?v= cache-buster, or a legacy /object/public/photos/… URL written before the lockdown. Legacy rows were never rewritten; every read path normalises instead, and only paths are ever written now.
  • signedPhotoUrls.ts — the signer. Batches up to 100 paths per request, caches results in memory keyed by the reference rather than the path (so the cover's cache-buster still busts the cache), treats a URL as expired five minutes early so it never dies mid-render, and returns a map containing only what resolved. A photo that cannot be signed is simply absent — callers render a placeholder. A missing photo is never a thrown error.

Two TTLs, chosen for different threat models: 60 minutes for in-app rendering, because a leaked URL is valid until it expires; 7 days for exported Markdown and HTML, because a shared file is read outside the app and its images must outlive the session, but a forwarded export should not become a permanent handle. The cache is cleared on SIGNED_OUT so one user's URLs never survive into the next user's session on a shared device.

Uploads are resized to a 1200 px longest edge and re-encoded as JPEG at 0.75 quality before leaving the device. Paths are deterministic — {userId}/{noteId}/{index}.jpg, and {userId}/trip-covers/{tripId}.jpg for covers with upsert: true, so replacing a cover overwrites rather than orphaning. The first path segment being the user id is what makes the storage RLS policies expressible at all: (storage.foldername(name))[1] = auth.uid()::text.

08Location provenance

The subtlest subsystem in the app, and the one that exists because of a real, repeated bug: a note typed up about Paris, at home in California, was tagged "Mountain View" — because that is where the phone was when the words were written.

The fix was not better GPS. It was to stop treating a coordinate as a fact and start treating it as a claim with a source. notes.location_source records which of four things produced the coordinates, and every downstream rule keys off it.

The same rules run in three places. At capture, resolveAutoLocation decides live in the sheet, so the user sees the corrected location before saving and can override it. At launch, two idempotent background passes fix history: sweepNoteLocations re-judges existing gps and legacy null-source notes against their trip's anchors, then backfillPlaceNames resolves missing place names. They run strictly in that order, so no geocode is spent on coordinates the sweep is about to rewrite.

Decision
Place-name precedence: manual > AI-extracted venue > geocoder label
Problem
The device reverse-geocoder returns name ?? street ?? city — usually a street, not the venue. Claude's tag-note pass does extract the real venue from the note text ("dinner at Ichiran"), but the original merge rule (existing ?? suggestion) let the street label pre-empt it.
Fix
mergeTags now returns the user's typed name when location_source === 'manual', otherwise prefers the AI venue over the geocoder label.
Why it matters
place_name is the dedupe key for the community layer and the only field published from it. Street labels would neither dedupe nor read as places on the shared map.
Known limitation, documented in code

A sweep rewrite to inferred is one-way. The note leaves the candidate set and is never re-evaluated, so if the anchor set was incomplete at the time — one destination failed to geocode while others succeeded and got cached — a note can be corrected to a plausible-but-wrong anchor permanently. Recovery is a manual edit, which marks it manual.

09The AI layer

Three Deno edge functions. The client holds no model key and no service role key, so every AI call is shaped as a function invocation. The division of labour between them is a cost decision as much as a capability one.

FunctionModelShapeWhen it fails
detect-intent Haiku 4.5, 60 max tokens Synchronous. Classifies a voice transcript as save vs. search. Client races it against a 6 s timeout and falls back to save. Never blocks capture.
tag-note Haiku 4.5, 120 max tokens Synchronous. Returns category, venue, city as JSON. Non-200 leaves the note tagging_status = 'pending'; the next drain retries. The note is already saved.
generate-blog Opus 4.8, vision, 16 000 max tokens Asynchronous. Inserts a generating row, returns its id, continues in the background. Writes error or insufficient to the row. Three independent timeouts back it up.
Decision
Verify the JWT in the function body, not only at the gateway
What was wrong
tag-note and detect-intent originally checked only that an Authorization header existed. Bearer hello passed. They were safe only because of the platform's verify_jwt dashboard default — a setting no function asserted, and one deploy with --no-verify-jwt would have published an unauthenticated proxy to the Anthropic key.
Fix
_shared/auth.ts → requireUser(req) performs a real admin.auth.getUser(token) and returns a ready-to-return 401 on failure, never a partial result. generate-blog already did this and goes further: it re-reads the trip's user_id and rejects with 403 unless it matches the token's subject, because the service-role client it uses bypasses RLS entirely.
Principle
A guarantee that lives in a dashboard toggle is not a guarantee. It belongs in code that ships with the function.

Blog generation: a long job on a platform with a wall clock

A photo-rich trip is far too much work for one HTTP response. The function inserts the row, returns the id in milliseconds, and hands the real work to EdgeRuntime.waitUntil(). The client never polls — it subscribes to blog_posts over Realtime and the card flips from Generating… to Ready to review on its own.

The vision pass is where the cost lives, and it is bounded on three axes. Photos are downloaded with the service role, decoded, resized to a 1536 px longest edge and re-encoded at JPEG 80 — roughly 3× cheaper in image tokens than full resolution, and ample for judging composition. At most 24 photos are sent as images; the rest are listed by id only, so they stay selectable but unjudged. Preprocessing runs concurrently in batches of 5, which keeps peak memory to five decoded images while cutting wall-clock enough that a 68-photo trip finished in ~54 s of a 140 s budget.

The three timers matter because they cover different failures. The AbortController covers a slow Anthropic response. The client's isStaleGenerating (3 minutes) covers a worker killed mid-flight, and offers retry. The pg_cron job (every 5 minutes, failing anything generating older than 5 minutes) covers the case where the client never comes back at all — safely beyond any legitimate run, so it can never kill a live generation.

Decision
Photo ids are opaque storage paths, and the model's output is filtered against a known set
How
Each image in the prompt is labelled with its storage path and the model is told these are opaque identifiers, not web addresses. On the way back, keepKnown() discards any id that was not actually offered.
Why
A hallucinated path would fail to sign on the client anyway, but a null cover is a better outcome than a permanently broken hero image. The same defensiveness runs on both sides of the boundary: the function does a coarse structural check on the itinerary, and the client's parseItinerary re-narrows every field, dropping malformed stops and empty days.

Before spending a token, a free client-side gate runs: at least 3 notes and 80 characters of text. It is deliberately lenient — the model's own judgment is the real quality check.

Drift worth noting

The original spec named claude-sonnet-4-6 for all AI work and Cohere embeddings for semantic search. Shipped reality: Haiku for the two cheap classification jobs, Opus with vision for the one expensive per-trip job, and no embeddings at all. pgvector is enabled by migration 001 and has never been used.

10The community layer

The only data that crosses from private to public. Completing a trip aggregates its named, categorised places into public_places — an anonymised table holding no user_id, no timestamps of visit, and no note prose. Just place identity, running-average coordinates, visit and rating counts, and a category tally.

Decision
A separate, unreadable ledger for idempotency instead of a computed diff
How
public_place_contributions holds one row per contributing note, with note_id unique. RLS is enabled with no policies at all — it is fully unreachable by anon and authenticated; only the definer function, running as table owner, touches it.
Why
It makes "count this note once, ever" a database constraint rather than application care. A trip can be re-completed, a note re-tagged, a backfill re-run — the counts stay correct. And because the ledger is the one structure linking a private note to a public place, it must never be readable; RLS-with-no-policies is the strongest available statement of that.
Cost
The aggregate is add-only. Deleting a note removes its ledger row but does not decrement public_places, so counts drift upward over time. Accepted for V1.

Place identity is a normalised key — lowercased, trimmed, whitespace-collapsed name and city joined by | — computed by an immutable SQL function that is also used directly by the SQL tests, so the tests exercise the same code the trigger does. Coordinates accumulate as a running average with a coord_count, so places gain precision as more people record them. The public_destinations view is declared security_invoker = on so it honours the underlying table's RLS rather than the view owner's rights.

11Security posture

The trust model in one line: the anon key ships inside the app binary, so anything the anon role can do, a stranger can do. Every policy is written against that assumption. A pre-beta audit in August 2026 found three places where it had not been, all fixed in one pass before any tester data existed.

SeverityFindingFix
Critical photos bucket had TO public SELECT, which backs the storage list API — the anon key could enumerate every user's folder and download their photos. Migration 025: owner-scoped SELECT, bucket flipped private, client rewritten to store paths and sign at render time.
High profiles SELECT was using (true) with no role clause — anon could dump every UUID, real name and signup time, which chains with the above into targeted deanonymisation. Migration 025: own-row only. Nothing in V1 reads another user's profile; the aggregate function is SECURITY DEFINER and unaffected.
Medium tag-note and detect-intent checked only that an Authorization header existed. _shared/auth.ts with a real token verification, asserted in the function body.

Both database findings predated the audit and had the same origin: they were written permissively for a public-blog feature that was later deferred to V2. The feature never arrived; the permissions stayed. That is the generalisable lesson — permissions granted for planned functionality outlive the plan, and nothing in the system notices.

Secret handling is deliberately narrow. EXPO_PUBLIC_* variables are compiled into the bundle and treated as public. The service role key exists in exactly two places: the local .env, which is gitignored, and the Supabase function environment. The GitHub Actions keep-alive workflow carries a comment stating it must never be added there.

12Build, release and operations

Builds

EAS with three profiles — development (dev client, internal), preview (internal distribution), production (auto-incrementing, remote version source). Local iOS builds run through npm run ios, which does pod install, then a patch script, then expo run:ios --no-install.

scripts/patch-ios-pbxproj.js is the kind of thing worth documenting rather than hiding: an idempotent post-prebuild patcher that fixes path-with-spaces breakage in the generated Xcode project. The project directory contains spaces, and expo prebuild writes shell invocations that do not survive them. Because ios/ is regenerated and gitignored, the fix has to be a script rather than a committed edit.

Schema changes

Migrations are applied through the Supabase MCP server rather than the CLI, then TypeScript types are regenerated and committed alongside. The workflow is written down in supabase/README.md because it is a two-step that is easy to half-do — a migration without regenerated types compiles until it doesn't.

Keeping the lights on

One GitHub Actions workflow, every three days: a curl against public_places using the anon key. Supabase free-tier projects auto-pause after ~7 days idle, and the failure mode is specific and bad — a tester's app silently stops saving notes mid-trip, and their trip cannot be repeated. It targets the one genuinely public table so no elevated credential is needed, and uses curl -f so a paused project turns the job red instead of passing silently.

Tests

362 tests across 40 suites, all passing, jest-expo preset. The distribution follows the layering: heavy coverage of pure helpers (merge rules, distance maths, markdown, ranking, validation), mocked-Supabase coverage of services, render tests for the components with real conditional logic. SQL-level behaviour has its own test files under supabase/tests/. There is no E2E layer; device QA is manual and recorded in docs/progress.md.

Documentation as an artifact

Every feature has a spec and a plan committed under docs/superpowers/ — 21 specs and 34 plans across the project's life — and docs/progress.md is a 771-line running record of decisions, bugs found in QA, and deferrals with reasons. Most of the "why" reconstructed in this paper came from there rather than from the code.

13How it behaves when things break

A useful way to read an architecture is to ask what happens when each dependency fails. Notebound answers this unusually well for the capture path and unevenly elsewhere.

FailureBehaviourRecovery
No network at captureNote saves locally and appears in the feed immediately, photos includedAutomatic on reconnect, foreground, or next launch
Photo upload fails repeatedlyNote is unaffected; card shows ⚠ N photos failedStops after 5 attempts; needs a manual re-add
tag-note downNote keeps tagging_status = 'pending', shows without a categoryRetried on every subsequent drain
detect-intent down or slow6 s timeout, falls back to saveNone needed — the fallback is the common case
generate-blog worker killedRow would stick on generatingClient marks it stale at 3 min; pg_cron fails it at 5 min
Geocoder unavailableLocation field keeps the typed label, drops the pin rather than storing bad coordinatesBackfill retries on the next launch
Storage unreachable at renderSigning returns nothing for that photo; a placeholder renders. Failures are never cachedNext render retries

Anthropic outageTagging and blog generation stall; notes and photos unaffectedAutomatic for tagging, manual retry for blogs

The pattern is consistent and intentional: the capture path degrades to fully local, and every AI enrichment is optional and retryable. Nothing the user typed is ever at risk of a network failure.

14Where the architecture is thin

An honest paper names what is not built. These are gaps in the shipped system as of this commit, not speculation.

GapStateConsequence
In-app account deletion Missing App Store Guideline 5.1.1(v) requires it for any app with account creation. Needs a delete-account edge function — the client can never hold the service key. Hard rejection at review.
Community opt-out Orphaned profiles.contribute_to_community exists, defaults true, and is honoured by the aggregate function — but nothing in src/ reads or writes it. The column appears only in generated types. Users contribute by default with no way to decline.
Search Shell SearchScreen is static placeholder markup. No query runs. pgvector was enabled in migration 001 for semantic search that was never built; the voice intent classifier can return search, and the handler just navigates to the tab.
Explore moderation Unresolved public_places.place_name is user-typed free text shown to other users. Guideline 1.2 requires filtering, reporting and blocking for UGC. The documented decision was to hide Explore for v1.0; the tab is still wired into TAB_CONFIG.
Rate limiting None generate-blog runs an Opus vision pass at roughly $0.12–0.65 per call with no per-user cap. Any authenticated user can loop it against their own trips.
Public web layer Deferred "Published" is a local status marker only. There is no web URL for a published post — the export-to-Markdown/HTML share sheet is the entire distribution story. This is the deferral that left the over-permissive policies behind (§11).
Community counts Add-only Deleting a note leaves its contribution counted. Visit counts drift upward permanently.
Realtime reducer Duplicated The same insert/update/delete reduction is written out in four hooks. Harmless, but it is the same bug surface copied four times.

Three of these — account deletion, the orphaned opt-out, and the Explore moderation posture — are release blockers rather than architectural debt. The rest are the ordinary residue of a V1 that kept its scope honest.
